# Архитектура hix

    +--------------------------------------------------------------+
    |  qubix: shell, процессы, VFS, tty, syscalls (int 0x80)         |
    +-----------------------------+--------------------------------+
    |  aether: task/thread, scheduler, ports/IPC, vm, heap           |  steel
    +-----------------------------+--------------------------------+  (графика)
    |  drivers: vga, bga, pci, serial, pit, rtc, ps2 kbd/mouse       |
    +--------------------------------------------------------------+
    |  hix core: boot, GDT/TSS/IDT/PIC, traps, printk, panic        |
    +--------------------------------------------------------------+
    |  rust/hix-core: ChaCha20-Poly1305 via SYS_crypto (optional)  |
    +--------------------------------------------------------------+

## Загрузка (`kernel/main.c`)

GDT/IDT/PIC → консоли (serial + steel) → `pmm_init` → `vm_init` (страничная
память) → `kalloc_init` → `task_init`/`sched_init` (загрузочный контекст становится
потоком `idle`) → драйверы → `qubix_init` → поток `init` → `init` (pid 1) →
`splash` (один раз, если включён) → `sh`.

Конфигурация загрузки (`config/hix.conf` → `build/hixconfig.h`) задаёт splash,
его длительность, quiet-режим VGA и скринсейвер с таймаутом простоя. Поверх неё
`kernel/bootconfig.c` разбирает `hix.*` из командной строки Multiboot
(`hix.splash`, `hix.quiet`, `hix.screensaver`, `hix.timeout`, `hix.safe`) и
отдаёт `sysctl hix.boot`/`kern.cmdline`. `steel/console.c` в quiet-режиме
пропускает info/notice, но `kernel/printk.c` по-прежнему пишет всё в кольцевой
лог и на COM1; `dmesg` остаётся полным. COM1 зеркалит tty (`qubix/tty.c`),
поэтому serial — полноценная консоль, а не только лог. Стартовый экран и
скринсейверы (`qubix/splash.c`, `qubix/screensaver.c`) — обычные программы
qubix, которые рисуют через `libq`/`int 0x80`.

## aether
- **pmm** — битовая карта страниц, непрерывные выделения.
- **vm** — страницы 4 КиБ: страница 0 не отображена (NULL → фолт), `.text/.rodata`
  только для чтения, у каждого стека потока — guard-страница. Переполнение
  стека ловит double-fault на отдельном TSS-стеке и печатает диагноз.
- **kalloc** — куча с граничными тегами, magic-проверки, double free = panic.
- **task/thread/sched** — задача = контейнер ресурсов (порты), поток = исполнение;
  round-robin с квантом 50 мс, вытеснение на выходе из прерывания, `ctx_switch` в
  `arch/x86/switch.asm`. Блокировки: `spin_lock_irqsave` (короткие) и `mutex`
  (длинные); ожидание — `waitq_wait_irq`.
- **ipc** — порты с правами SEND/RECEIVE, имена с «поколением», сообщения с
  reply-портом, таймауты, bootstrap-сервис имён (`hix.upper` в демо).

## qubix
- Один `int 0x80`: положительные номера — вызовы процессов (`write`=4,
  `wait4`=7, `ioctl`=54 …), отрицательные — порты aether (`AE_*`, например
  `ae_msg_trap`=-31), `kill`=37, `steelctl`=500, `SYS_gantry`=600,
  `SYS_crypto`=601.
- `proc` = оболочка над `task`: pid, fd-таблица, `wait4`, зомби. `kill(pid)` ставит
  флаг `killed`, процесс завершается (статус 137) на ближайшем системном вызове;
  спящий в ожидании без таймаута проснётся только после события. pid 0 и 1 неприкосновенны.
- tty имеет сырой режим (`ioctl`), на нём построен редактор строки шелла.
- Программы (`qubix/progs.c`, `shell.c`) используют только `libq.h` — то есть
  syscalls; когда появится ring 3, они переедут без переписывания.
- `sysctlbyname` отдаёт текст: `kern.*` (включая `kern.cmdline`), `hw.*`, `hix.ps`,
  `hix.devtree`, `hix.dmesg`, `hix.boot`, `hw.display`, `hix.desktop`, `hix.crypto`.
- `hixfetch` (`lib/hixfetch.c`) — логотип и сведения о системе, общий для шелла и Term.

## steel
`steel_device` → `steel_surface` → `steel_cmdbuf` (записал команды — `commit`) →
`steel_layer` + композитор → консоль с ANSI-цветами и прокруткой.

Два бэкенда: VGA-текст и **пиксельный** (`gfxdev`/`pixdev`). Драйвер `bga`
находит адаптер Bochs VBE по PCI, ставит 1024x768x32, фреймбуфер берёт из BAR0
(он попадает в существующие некэшируемые 4-МБ страницы). `pixdev` рисует клетки
80x25 гладким шрифтом 12x28 и подставляет вместо «дырок» (`STEEL_HOLE`)
холсты зарегистрированных клиентов. `canvas`/`gfx.h` — ARGB-холст: заливка,
скруглённые прямоугольники, текст, блиттинг с альфой. Курсор мыши рисуется ядром
с сохранением фона, программам код курсора не нужен.

**Кадр и плавность.** `pixdev` рисует в чистую копию экрана в обычной памяти
(`fb`), а в видеопамять переписывает только изменившиеся отрезки строк
(`flush`): чтение и альфа-смешивание прямо в видеопамяти очень медленны.
Окно, которое тащат мышью, показывается как **спрайт** (`pixdev_float`,
`STEEL_CTL_FLOAT`): оно следует за курсором попиксельно с мягкой тенью, а фон
под ним не перерисовывается; при отпускании окно встаёт в ближайшие клетки.
Курсор не хранит фон под собой, а накладывается поверх при каждом `flush`.

**Панели** (`steel/panel.cpp`, `include/steel/panel.h`): сетка 960x700 стоит в
экране 1024x768 на y=24, так что сверху остаётся полоса 24 px, снизу — 44 px.
Это панели, и они не состоят из клеток: desk описывает их структурой
`steel_panel` (меню, часы, кнопки окон), `STEEL_CTL_PANEL` передаёт её ядру,
`pixdev_panel` перерисовывает панели, только если структура изменилась.
`panel_hit` отвечает, что находится под пикселем. Обои — процедурные
(`wall_px`): звёздное небо с млечным путём и силуэтами столовых гор.

## desk
Рабочий стол — процесс qubix (`apps/`, `include/desk/`). События от клавиатуры и
мыши (`qubix/input.h`) приходят через `steelctl(STEEL_CTL_EVENT)`, готовый кадр
уходит через `STEEL_CTL_PRESENT`; пока desk держит экран, консоль приостановлена.
Программы — таблица `struct app` (`apps/desk_apps.c`), у каждого окна своя
поверхность и 8 КБ приватной памяти, так что аллокатор не нужен. Пиксельная
программа (Chess) владеет холстом и регистрирует его в steel; события мыши
приходят с точностью до пикселя. Backend
(`struct desk_backend`: события, показ, время, панели, питание) подменяется в
тестах скриптом событий. Глобальные меню **Apps** и **Computer** на верхней
панели (F9 — с клавиатуры) открываются как обычные клеточные выпадающие меню;
кнопка окна на нижней панели поднимает, сворачивает или восстанавливает окно.

## Gantry
Общее имя платформы над всеми ядрами (по роли — как Darwin над XNU; драйверная
модель — как IOKit). Написан на C++ (`gantry/`, `include/gantry/gantry.h`), чистое
C-ядро о нём ничего не знает: `kernel/main.c` один раз зовёт `gantry_boot()`.
- **Реестр** — дерево `Node` (имя, класс, до 8 свойств, дети): Root → hix, drivers
  (по узлу на каждый C-драйвер), pci0 (устройства шины). `sysctl hix.registry`,
  команда шелла `registry`.
- **Драйверы** — классы `Driver` (`probe` даёт оценку, `start` запускает);
  `GANTRY_DRIVER(Класс, "ПровайдерКласс")` регистрирует фабрику. Для каждого узла
  побеждает драйвер с лучшей оценкой и становится его дочерним узлом. Встроены
  `GenericPCI` (запасной, определяет тип устройства) и `BochsDisplay` (1234:1111).
- Пока это описание и подбор: сами C-драйверы (`drivers/`) работают как раньше и
  переезжают под Gantry постепенно. Kit — SDK для пользовательских программ —
  будет построен на тех же классах.

## Rust в ядре (необязательно)

`rust/hix-core` — `no_std` staticlib для `i686-unknown-linux-gnu`, собранный
стабильным rustc и слинкованный в `build/hix.elf`. Он не вызывает Linux и не
аллоцирует; ABI `hix_rust_*` принимает только буферы, уже скопированные ядром.
Сейчас модуль реализует ChaCha20-Poly1305 (RFC 8439). `SYS_crypto` (601) —
единственная точка входа; `qubix/crypto.c` проверяет указатели ring 3,
копирует данные в ядро и затирает ключи. Без i686-core ядро собирается, но
вызов возвращает `-ENOSYS`. Подробности и порядок замены шифра —
[docs/CRYPTO.md](CRYPTO.md).

## Языки
hix, aether-ядро и драйверы — C. Для слоёв выше есть C++ без рантайма
(`lib/cxxrt.c`, `lib/new.cpp`, секция `.init_array` в `linker.ld`). Rust
необязателен и живёт за C ABI; Python — инструмент хоста (генераторы,
векторы в `scripts/crypto_check.py`), в ring 0 он не попадает.

## Дальше (после 1.0.0)
Дисковая ФС и установка на диск, SMP, безопасный API окна для ring 3, фреймбуфер
из GRUB как запасной путь для пиксельного режима и композитор слоёв вместо
клеточной сетки. Ring 3, отдельные адресные пространства и ELF-загрузчик уже
работают — см. следующий раздел.

## Кольцо 3 (0.5.0, этап 1)

Адресное пространство пользователя (`struct uspace`) — свой page directory. Записи
ядра (тождественное отображение ОЗУ, окна устройств) копируются из каталога ядра и
указывают на те же таблицы страниц, без бита U. Приватное окно —
`USER_BASE..USER_TOP` (0x40000000–0x80000000), выше ОЗУ, поэтому не пересекается с
тождественным отображением. Загрузка: `elf_parse` → `uspace_load_elf` (сегменты, потом
стек из 8 страниц). Процесс начинается как обычный поток ядра, который в
`uspace_exec` превращает себя в пользовательский (`enter_user`, `iret`). Возврат только
через ловушку на стек ядра из `TSS.esp0`; `schedule()` вызывает
`arch_thread_switch`, который выставляет esp0 и CR3 следующего потока.

Безопасность: ошибка страницы или #GP при `cs & 3 == 3` ведёт в `arch_user_fault`
(процесс завершается); для кольца 3 `user_ok` проверяет только страницы с битом U
своего пространства, с учётом права записи; белый список вызовов. `SYS_crypto`
(601) разрешён и проверяет каждый указатель до копирования. Проверено на хосте
(разбор ELF, построение таблиц) и загрузкой в QEMU.

## Gantry: сервисы и Kit (0.6.0)

Gantry теперь не только реестр устройств. `Service` — узел реестра с методом
`call(op, msg)`; `Services` хранит таблицу (16 сервисов). `Notifier` рассылает события
подписчикам ядра и считает их по темам; `Properties` — плоское дерево ключ/значение.
Встроенные Kit — `kit.system`, `kit.prop`, `kit.notify`. Программа кольца 3 вызывает
их через `SYS_gantry`; ядро копирует `kit_msg`, проверяет указатели по адресному
пространству процесса и разрешает запись только под `user.`. Образ программ для `/bin`
собирается `scripts/mkapps.py` и распаковывается `qubix/initfs.c`. Подробнее — SDK.md.
