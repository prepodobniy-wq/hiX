# Как участвовать в hix

Спасибо, что смотрите на hix. Проект небольшой и намеренно честный: лучше
небольшой работающий код с тестом, чем большая недоделанная подсистема.

## Прежде чем менять код

- Прочитайте [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) и
  [docs/CODING-STYLE.md](docs/CODING-STYLE.md).
- Для загрузки, splash и скринсейверов — [docs/BOOT.md](docs/BOOT.md).
- Для ring 3 и SDK — [docs/SDK.md](docs/SDK.md).
- Для Rust-модуля и `SYS_crypto` — [docs/CRYPTO.md](docs/CRYPTO.md).

## Сборка и проверка

    make                 # обычная сборка
    make strict          # -Werror, чистая сборка
    make test            # хостовые тесты
    make verify          # всё: стиль, Multiboot, тесты, Rust, crypto, кадры
    make smoke           # загрузка в QEMU через COM1

Перед PR прогоните хотя бы `make verify`; если меняется загрузка или
syscall — ещё и `python3 scripts/smoke.py --require-rust`.

## Стиль

- C11 для ядра, без libc; табы, Linux coding style, строки до 100 колонок
  (лучше 80), `// SPDX-License-Identifier: GPL-2.0-only` в начале файла.
- C++ только для слоёв выше ядра, без исключений, RTTI и стандартной
  библиотеки. Ядро hix остаётся на C.
- Rust — только за C ABI (`include/hix/*abi.h`), `no_std`, без аллокаций.
- Python и bash — инструменты хоста; в ring 0 они не попадают.
- Новый номер версии не добавляйте в код, Makefile или тесты: только
  `include/hix/version.h`. README и заметки о выпуске могут упоминать
  текущий релиз, но перед тегом сверяйте его с `make version`.

`make check` проверяет табы, хвостовые пробелы, длину строк и SPDX. Если
правило можно проверить механически, лучше добавить проверку, чем абзац в
документации.

## Тесты

- Логика ядра и библиотек — в `tests/` (хост, `-DHIX_HOST_TEST`).
- Новый syscall ring 3 — тест в `tests/test_uspace.c` или `test_sdk.c`.
- Новый qprog/шелл — тест в `tests/test_shell.c` или `test_desk.c`.
- Кадры пиксельного вывода — `make shots` и `make shots-golden` (только если
  изменение внешнего вида намеренное).
- Rust — `make rust-test` и `make crypto-test`.

## Коммиты и PR

- Один коммит — одна причина изменения. Сообщение в повелительном
  наклонении, коротко: `qubix: fix GANTRY_LOOKUP argument`.
- Не смешивайте рефакторинг и поведение в одном коммите без необходимости.
- В PR опишите, что проверено: команды, хост, QEMU, до/после.
- Не удаляйте чужие файлы и не переписывайте историю без обсуждения.

## Чего не делать

- Не добавлять гостевой bash: qubix использует свой шелл.
- Не тащить libc, аллокатор или стандартную библиотеку в ядро.
- Не включать SSE/MMX в код ядра: ядро не сохраняет SIMD-состояние.
- Не обещать установку на диск, SMP или права доступа в документации, пока
  их нет в коде.
- Не публиковать релиз без `make release` и проверки `SHA256SUMS`.
